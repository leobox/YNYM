## 📝 실제 상태와 검증
스캐폴딩(`docker-compose.yml`, `init.sql`, Grafana provisioning, `tools/sync-postgres.mjs`)은 오늘 자 최초 커밋에 이미 포함돼 있었으나 backlog에는 `todo`로 남아 있었음. 실제로 기동·검증해 완료 처리함.

- `cd infra/monitoring && docker compose up -d` → `leobox-postgres`(healthy), `leobox-grafana` 정상 기동
- `node tools/backlog.mjs sync-db` → backlog.json 11개 작업 → PostgreSQL `tasks` 테이블 UPSERT 성공
- `v_backlog_summary`, `v_tasks_by_category` 뷰 조회 정상 (진행률 72.7%, 카테고리별 집계 일치)
- Grafana `/api/health` OK, 프로비저닝된 데이터소스·대시보드(`Leobox Multi-root Backlog Overview`, 패널 12개) 존재 확인

## 🐛 발견 및 수정한 버그
`grafana/provisioning/dashboards/backlog_dashboard.json`의 모든 패널이 데이터소스를 `uid: "PostgreSQL-Backlog"`로 하드코딩 참조하는데, `grafana/provisioning/datasources/postgres.yaml`에는 `uid`가 지정되어 있지 않아 Grafana가 임의의 uid(`P2F6777A5C82D4805`)를 자동 생성함. 결과적으로 **대시보드의 패널 12개 전부가 "Data source not found" 에러**를 냈음 (`/api/ds/query`로 직접 재현 확인).
- 수정: `postgres.yaml`에 `uid: PostgreSQL-Backlog` 명시 추가.
- 이미 다른 uid로 프로비저닝된 상태가 Grafana의 영속 볼륨(`grafana_data`, SQLite 내부 DB)에 남아있어 재시작만으로는 반영되지 않고 컨테이너가 크래시 루프에 빠짐(`Datasource provisioning error: data source not found`) → `docker compose down` 후 `monitoring_grafana_data` 볼륨 삭제, 재기동으로 해결. (Grafana 상태는 오늘 처음 만든 것으로 보존할 사용자 데이터 없음 확인 후 삭제.)
- 수정 후 `/api/ds/query`로 대시보드의 실제 SQL(진행률, 카테고리별 집계 등) 재실행해 정상 응답 확인.

## 🖥️ 별도로 해결한 로컬 환경 문제 (Docker Desktop / WSL)
작업 중 Windows 계정 폴더명 변경(`leobo`→`leobox`) 여파로 `Ubuntu` WSL 배포판이 깨져 있었음 (레지스트리 `BasePath`가 존재하지 않는 옛 경로를 가리킴; 실제 vhdx는 새 경로에 존재, 데이터 손실 없음). 사용자 승인 하에 `HKCU:\...\Lxss\{144f1185-...}`의 `BasePath`를 새 경로로 교정 후 `wsl --shutdown`으로 정상화. Docker 엔진(`docker-desktop` WSL 배포판)은 이 문제와 무관하게 항상 정상 동작 중이었음.

## 🚧 남은 한계 / 후속 과제
- `sync-db`는 수동 명령이며 훅/크론으로 자동화되어 있지 않음 (변경 시마다 직접 실행 필요). 본 작업 범위인 "초기 설정 구축"을 넘어서므로 자동화는 별도 backlog 항목으로 판단.
- Postgres(`leobox`/`leobox_secret`), Grafana(`admin`/`admin`) 자격증명이 compose 파일에 평문 하드코딩되어 있음. 포트가 로컬호스트에만 바인딩되는 순수 로컬 개발용 인프라라 당장 위험도는 낮지만, 외부 노출 환경으로 옮길 경우 반드시 `.env`/시크릿 관리로 교체할 것.
